History of DBMS and when not to use DBMS

Introduction

A database is an organized collection of data. A database management system (DBMS) is the software that sits between that data and the people or programs using it. It stores the data, finds it, changes it and protects it, so every application doesn’t have to rebuild those jobs from scratch.

Before DBMSs, each program usually kept its data in its own files. The same facts ended up copied in several places and drifted out of sync, and changing a file’s layout meant rewriting every program that read it. A DBMS replaced that with one shared home for the data and a set of guarantees: many users can work at once, the data stays correct, access can be controlled, and everything can be recovered after a failure.

That idea is about sixty years old, and it has been reinvented several times. Each new kind of database appeared because the previous kind hit a limit. This post does two things. First, it walks through that history, so you can see why relational, NoSQL and vector databases each exist. Second, it covers when you should not use a DBMS at all, because the simplest tool that does the job is often the right one.

A short history

  1. 1960s

    File systems, IDS and IMS

    The first real DBMSs arrived with hierarchical and network models. Powerful, but rigid: you had to know the access paths in advance.[1]

  2. 1970

    Codd’s relational model

    Data as plain tables, independent of how it’s stored. This idea shaped the next fifty years.[2]

  3. 1970s

    System R, INGRES and SQL

    Proved the relational model was practical, and gave us a query language that’s still everywhere.

  4. 1980s

    Oracle, DB2, SQL standardized

    ANSI standardized SQL in 1986. Relational became the industry default.

  5. 1990s

    MySQL, PostgreSQL, data warehouses

    Open source and analytics went mainstream, and PostgreSQL grew out of Berkeley’s POSTGRES project.

  6. 2000s

    Bigtable, Dynamo, MongoDB, Redis (NoSQL)

    Web-scale apps needed scale and flexible schemas, and accepted weaker consistency to get them.[3]

  7. 2010s

    Spanner, cloud-managed DBs, NewSQL

    Distributed SQL with strong consistency, run for you by a cloud provider.[4]

  8. 2020s

    Vector, serverless and multi-model

    Built for AI and embedding search, with elastic scaling.

The pattern: each wave fixed the previous one’s pain. Files had redundancy, hierarchical models were rigid, relational struggled with massive scale, and NoSQL traded some consistency for that scale.

When not to use a DBMS

A DBMS is powerful, but it isn’t free. Skip it in these cases:[5]

  • Your data is small and simpleA config file, a to-do list or a one-off script is fine with JSON, CSV or plain files.
  • The app is fixed and single-userWith no concurrent access, you pay for locking and transactions you’ll never use.
  • You have hard real-time constraintsA DBMS’s generality adds overhead that can break strict timing, as in embedded or control software.
  • The data is mostly big blobsVideos, images and backups belong in object storage like S3, with only metadata in a database.
  • You can’t afford the overheadLicensing, setup, admin skills, backups, security hardening and tuning all cost time and money.[3]
  • You need heavy analytics on huge raw dataA general-purpose transactional database is the wrong tool. Use a data warehouse or columnar engine.
  • The schema is completely unpredictableForcing it into rigid tables can cost more than it gives.

Takeaway

Use a DBMS when you need shared access, integrity, security and recovery. If you need none of those, you’re adding complexity for nothing. Learn the history to understand why each database type exists, then pick the simplest tool that does the job.
